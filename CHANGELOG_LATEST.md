# Changelog

For more details go to [emsesp.org](https://emsesp.org/).

## [3.10.0]

This release is primarlity a security hardening one. Please read the Breaking Changes below carefully before upgrading.

## **Breaking Changes**

A full list of breaking changes can be found in this [discussion](https://github.com/emsesp/EMS-ESP32/discussions/3417)

1. **Make a System Backup before upgrading** (Settings > Download/Upload). Passwords are stored hashed after the upgrade and older versions can't read them, so going back to 3.8.x or 3.9.x needs this backup. Without it, see [Going back to an older version](https://docs.emsesp.org/FAQ#going-back-to-an-older-version).
2. **Factory passwords must be changed.** After signing in with a factory password, an admin must set a new admin password before the Web UI can be used. If no WiFi network is set yet, a new access point password is needed too. Integrations using API keys keep working in the meantime.
3. **Every `/api` call needs an API key, also reads, and access tokens are replaced by API keys.** Reading values without a token now gets HTTP 401. After the upgrade, create an API key in Security > API Keys for each integration, such as Home Assistant REST sensors, Prometheus, dashboards and scripts, including ones that only read, and send it as `Authorization: Bearer <key>`. MQTT isn't affected. Pick "Read" for integrations that only read values, "Read and Write" for ones that change settings or values. The key icon in Manage Users is gone. To read a value in a browser, open the `/api` address and sign in with your EMS-ESP user when the browser asks; this only reads. Integrations that can't send a key in a header, such as the ioBroker ems-esp adapter (7.0.8 and older), can have it in the address instead: set the EMS-ESP address to `http://iobroker:emsesp_...@<ip>` with a "Read and Write" key.
4. **Web UI sign-ins expire after 30 days**, and changing a user's password signs that user out on all browsers.
5. **Some `/api` calls need a "Read and Write" API key**: changing settings (for example `system/mqtt/enabled`) and reading the definitions of named Commands (`/api/commands/...`).
6. **"Bypass Access Token authorization on API calls" is removed.** Give each integration that called `/api` without a token an API key: "Read" to read values and run Commands that guests may run, "Read and Write" to change values, for example to set a temperature.
7. **Guest users have less access.** Only admins can open or change the Scheduler, Commands, Custom Entities and Modules, rename devices or change entity customizations. New Commands can't be run by guests until "Guests may run this command" is ticked; Commands from before the upgrade keep guest access. Entries made before the upgrade are kept, and Scheduler entries run with admin rights, so after upgrading check the Scheduler and Commands and delete any entry you didn't create, especially if guests or the API bypass were used.
8. **The live System Log needs a login**, also for tools that read `/es/log` directly.
9. **Tokens and API keys are only accepted in the `Authorization` header.** A token in the URL (`?access_token=...`) no longer works on `/api`, `/rest` or `/es/log`. Send `Authorization: Bearer <key>` instead, for example `curl -H "Authorization: Bearer emsesp_..." http://ems-esp.local/api/boiler`.
10. **Telnet changes.** Log in with a Web UI user: admin users get admin rights, `su` no longer works over telnet. At most 2 sessions at a time. On new installs telnet is off, turn it on in Application Settings if you use it.
11. **The Super User password is gone.** On the serial console, `su` asks for the username and password of a Web UI admin user. The `passwd` command and the Super User password field in Security settings are removed.
12. **Backups leave out passwords by default.** To move settings to a new device, tick "Include passwords and keys" when making the System Backup, and keep that file safe.
13. **MQTT `info` topic:** `IPv6 address` is now an array, and `IPv4 DNS Server` is replaced by a `DNS Server` array. Update any automations that read these fields.
14. **New installs have no `guest` user.** A fresh install or factory reset only creates `admin`. Add a view-only user in the setup screen or under Security > Users. Existing users are kept when upgrading.
15. **Web pages on other addresses need CORS to use `/api`.** A browser request to `/api` from a page on another address (for example a home-made dashboard) is refused with 403, unless CORS is enabled with that page's address as the origin, for example `http://homeassistant.local:8123`. Home Assistant's integration, Node-RED, scripts and `curl` are not affected. `*` still works but shows a warning.
16. **Opening the Web UI by another name needs that name allowed.** The IP address, the hostname and `<hostname>.local` always work. If you open EMS-ESP in a browser by another name, for example `ems-esp.fritz.box` or through a reverse proxy, open it once by its IP address and add the name under Network Settings > Allowed host names. Home Assistant, Node-RED and scripts are not affected.
17. **Only admins can pass their own value to a custom Command.** Guests and "Read" API keys can still run guest-allowed Commands, but only with the value stored in the Command. Values sent by non-admins (for example to `system/message`) can no longer fetch a `{"url":...}`; use an admin sign-in or a "Read and Write" API key, or store the URL in the Command or Schedule itself.
18. **Firmware that isn't an official EMS-ESP build asks before it installs.** Official releases and development builds are signed by EMS-ESP and install as before. Any other firmware, such as your own or a community build, or a filesystem image (`*littlefs.bin`), is stopped when uploaded in the Web UI, installed from a URL or uploaded in the Recovery, with "This is not an official EMS-ESP build"; click "Install anyway" to install it. The Version page then shows "Custom build". Flashing over USB isn't affected. Scripts that upload to `/rest/uploadFile` get HTTP 412 for such a file and can add `?custom=1` to install it anyway (`scripts/upload.py` and `scripts/upload_cli.py` do).
19. **Firmware, user and security changes ask for your password again.** Before uploading or installing firmware, switching the firmware partition, restoring a backup, downloading a backup with passwords, a factory reset, changing users or passwords, creating or revoking API keys, or turning on CORS, allowed host names or telnet, the Web UI asks for your password; it isn't asked again for 5 minutes. Scripts that do these with a Web UI sign-in token get HTTP 428 and must first send the password to `POST /rest/confirmPassword` with `{"password":"..."}`, or use an API key where one is accepted (API keys and MQTT aren't affected). Firmware can only be installed from a URL of an EMS-ESP release on GitHub (`https://github.com/emsesp/EMS-ESP32/releases/...`); for other files, upload them instead.
20. **Values outside their range are refused.** A write with a number below the entity's minimum or above its maximum (including a custom min/max set in Customizations) is now refused with `out of range` instead of being sent to the boiler or thermostat. Check automations that write values. In read-only mode, raw write telegrams (`send` commands) are no longer sent either; only raw read requests are. Turning read-only mode off asks for your password.
21. **Repeated and frequent writes are limited.** Writing the same value to the same entity again within a minute is skipped (the caller still gets OK), and more than 10 writes a minute to one entity, or 120 to all entities together, log a warning. Automations that write on every update keep working but send less to the boiler. This write protection is set in Application Settings next to read-only mode: the number of writes a minute, and whether writes over the limit are refused (HTTP 429, an MQTT error response or Modbus "server device busy"). Turning write protection off asks for your password.
22. **MQTT no longer runs system commands by default, and ignores retained commands.** A new MQTT setting, "Commands received over MQTT", chooses between "Off, only read values", "Change values and run Commands" (the default) and "Everything, also system commands". Home Assistant only changes values, so it keeps working. Automations that publish to `system/...` topics, for example `system/restart`, `system/send` or `system/mqtt/enabled`, get "system commands over MQTT are turned off" until "Everything" is chosen, which asks for your password. A factory reset (`system/format`) and erasing the crash dump (`system/coredump`) are never accepted over MQTT. Commands published with the retain flag are ignored with a warning in the log, because the broker would send them again on every reconnect; publish them without retain.

## Added

- firmware rollback: a newly installed firmware is only kept once it has run for 2 minutes or is restarted from EMS-ESP. If it crashes or loses power before then, the device goes back to the previous firmware, or to the Recovery if there is none. Needs the bootloader of 3.10.0, which only a flash over USB installs, a firmware upload keeps the existing bootloader
- after a crash, a summary of the core dump (task, PC and backtrace) is logged at boot and shown as `coredump` in `/api/system/info`. `call system coredump` erases it. Admins can download the full dump in Settings > Download/Upload, and the Recovery dashboard shows the summary with a download button. See `docs/Crash-Dumps.md` for how to decode it
- console on the System Log page: admins can run console commands such as `show values` from the WebUI and see their output
- the LED flashes white while the Recovery is running, using the LED GPIO and type from the Application Settings (also when the LED is set to hidden)
- uploading a settings file only changes the settings it contains, so a partial file can be used to change a few settings and keep the rest
- mock server test page `/rest/mockVersions` (e.g. http://localhost:3080/rest/mockVersions) to switch scenarios at runtime without restarting: the current, stable and dev versions, offline, official or custom build, DEBUG, the installed and online Recovery version, and the board's flash size (4MB, 16MB or 32MB) and PSRAM. It has presets for common cases and can sign in as admin or guest. Values can also be set in the URL, like `?flash=4MB&psram=false`, and `?reset` goes back to the defaults
- EMS devices that EMS-ESP polls and that send nothing for 5 minutes are reported offline: logged, published retained as `online`/`offline` to `ems-esp/status/<device>_<id>` (e.g. `ems-esp/status/thermostat_10`), and shown as `online` and `lastSeen` (seconds) per device in `/api/system/info`. In Home Assistant the device's entities become unavailable and each device gets a "status" connectivity sensor

## Fixed

- large numbers in analog sensor values (e.g. pulse counters above 1 million), custom entities and API/MQTT writes could be cut off or lose digits [#3367](https://github.com/emsesp/EMS-ESP32/issues/3367)
- with no EMS bus attached (e.g. only powered over USB), noise on the Rx line was taken for a bus: a single random byte matching our poll marked the bus as connected, after which every noise frame was logged as `Incomplete Rx` or `Invalid source` and counted as an error. A noise frame passing the CRC could also set the wrong EMS bus type. A poll to our bus id is now only trusted when the 3 telegrams before it all had a valid CRC, the bus type is taken from the poll, and nothing is processed before then
- RC300/RC310 `nofrostmode` missing `off` state [#3311](https://github.com/emsesp/EMS-ESP32/issues/3311)
- SRC/MX300 wireless room thermostats: `seltemp` and `mode` were written to the cooling settings on systems without a heatpump, so the change was ignored (since 3.9.0) [#3414](https://github.com/emsesp/EMS-ESP32/discussions/3414)
- Home Assistant entities of analog sensors disappeared after an MQTT reconnect or "Refresh MQTT" and only came back after a restart or saving a sensor (since 3.9.0) [#3422](https://github.com/emsesp/EMS-ESP32/issues/3422)
- thermostat switchtimes: setting one in JSON with `"day":"all"` cleared that slot and reported success, it's now refused [#3434](https://github.com/emsesp/EMS-ESP32/discussions/3434)
- custom entities on the EMS bus: a write of the value shown when the list was last saved was reported as done but never sent, until a restart [#3431](https://github.com/emsesp/EMS-ESP32/issues/3431)

## Changed

- security: Web UI sign-in tokens are signed with a random key that is unique to each device, so existing access tokens stop working after the upgrade. Admins see a notice in the WebUI until it is closed. Changing an admin password replaces the key, which signs everyone out
- security: Web UI sign-ins expire after 30 days (once the clock is set by NTP), and changing a user's password, or removing the user, signs that user out everywhere [#3353](https://github.com/emsesp/EMS-ESP32/issues/3353)
- security: API keys replace the per-user access tokens for `/api`. Admins create them in Security > API Keys with a name and "Read" or "Read and Write" access, and can revoke each one. A key is shown once when created and only stored as a hash. Read keys act like a guest user, Read and Write keys like an admin, and keys only work on `/api`, not for the Web UI [#3354](https://github.com/emsesp/EMS-ESP32/issues/3354)
- security: an admin who signs in while factory passwords are in use must set a new admin password first, plus an access point password if no WiFi network is set [#3357](https://github.com/emsesp/EMS-ESP32/issues/3357)
- security: a fresh install or factory reset no longer creates the `guest` user [#3357](https://github.com/emsesp/EMS-ESP32/issues/3357)
- security: a warning is shown while the access point still uses the factory password [#3359](https://github.com/emsesp/EMS-ESP32/issues/3359)
- security: firmware is signed by EMS-ESP (ECDSA P-256) in CI by `scripts/sign_firmware.py`. A Web UI upload, install from URL or Recovery upload of anything else, including filesystem images, is stopped and the Web UI asks before installing it as a custom build (`?custom=1` on `/rest/uploadFile`, `custom` on the `uploadURL` action). An official upload shows "Official build", and the Version page and the system info show whether the running firmware is an official or a custom build. Recovery 1.1.0 [#3369](https://github.com/emsesp/EMS-ESP32/issues/3369)
- security: only firmware built by this repository's GitHub Actions is signed, after approval by a maintainer; `SECURITY.md` explains what is checked [#3370](https://github.com/emsesp/EMS-ESP32/issues/3370)
- security: changes to the firmware, the users and the security settings from the Web UI need the password entered again, which counts for 5 minutes for that sign-in only and is kept in memory. Installing from a URL only accepts EMS-ESP releases on GitHub over HTTPS, also after redirects. `scripts/upload.py` and `scripts/upload_cli.py` enter the password again before uploading [#3371](https://github.com/emsesp/EMS-ESP32/issues/3371)
- security: writes check the entity's min and max, read-only mode also blocks raw write telegrams and turning it off needs the password, and the log line for each write says where it came from (Web UI, API, MQTT, Modbus, console or a custom command) with the user and IP address [#3372](https://github.com/emsesp/EMS-ESP32/issues/3372)
- security: a write of the value already sent to the same entity within a minute is skipped, and more than 10 writes a minute to one entity or 120 to all entities log a warning or, if chosen, are refused with HTTP 429. Writes from the Web UI, API, MQTT, Modbus, Scheduler and Commands all count; raw `send` telegrams count towards the total. The per-entity checks cover the 16 entities written most recently. `/api/system/info` shows `writesSkipped` and `writesLimited` [#3372](https://github.com/emsesp/EMS-ESP32/issues/3372)
- security: MQTT over TLS can check the broker with a CA certificate or with the SHA-1 fingerprint of the broker's own certificate (for self-signed certificates), chosen in the MQTT settings. Without a check the settings page and the log warn that the broker isn't checked [#3373](https://github.com/emsesp/EMS-ESP32/issues/3373)
- security: "Commands received over MQTT" setting: off (only reads), values and Commands (default) or everything. MQTT never runs a factory reset or erases the crash dump, and retained commands are ignored so a retained `system/restart` can't restart the gateway on every reconnect. `/api/system/info` shows it as `mqttCommands`
- security: a factory reset (Web UI, command, button or Recovery) now erases the whole filesystem partition before the restart, so old passwords and keys can't be read back from the flash. It also erases the crash dump, which holds a copy of the memory. Do a factory reset before selling or giving away a gateway [#3378](https://github.com/emsesp/EMS-ESP32/issues/3378)
- security: `SECURITY.md` describes how to report a vulnerability, which versions get security fixes, how fixes are published and the security model [#3380](https://github.com/emsesp/EMS-ESP32/issues/3380)
- security: the command parser and expression evaluator are fuzzed with AddressSanitizer and UBSan on every pull request (`pio run -e native-fuzz -t exec`). It found an unmatched `)` in an expression corrupting memory, an integer overflow in number parsing and a `%` in a command value being read as a log format, all fixed [#3368](https://github.com/emsesp/EMS-ESP32/issues/3368)
- security: hardened parsing of API, MQTT and expression input: large numbers, `%` by zero, very long numbers or hex values and oversized request bodies no longer crash the device. Request bodies are only read after the login check [#3367](https://github.com/emsesp/EMS-ESP32/issues/3367)
- security: custom Commands run by guests use the stored value only, and URL fetches in values only work in text saved by an admin (Commands, Schedules, Custom Entities) or sent by an admin [#3366](https://github.com/emsesp/EMS-ESP32/issues/3366)
- security: browsers can only open the device by its IP address, hostname, `<hostname>.local` or a name added under Network Settings > Allowed host names, against DNS rebinding. Requests from Home Assistant, scripts and through the access point are not checked [#3364](https://github.com/emsesp/EMS-ESP32/issues/3364)
- security: the Web UI is served with `Content-Security-Policy`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` headers [#3365](https://github.com/emsesp/EMS-ESP32/issues/3365)
- security: CORS needs an explicit origin, `Access-Control-Allow-Credentials` is no longer sent, and `/api` refuses browser requests from other sites unless their origin is allowed by the CORS setting [#3361](https://github.com/emsesp/EMS-ESP32/issues/3361)
- security: tokens and API keys are only accepted in the `Authorization: Bearer` header, no longer as an `access_token` URL parameter, so they don't end up in browser history or server logs [#3363](https://github.com/emsesp/EMS-ESP32/issues/3363)
- security: changing settings through `/api` (for example `system/mqtt/enabled`) needs a "Read and Write" API key
- security: the "Bypass Access Token authorization on API calls" setting is removed, use a "Read" or "Read and Write" API key instead [#3360](https://github.com/emsesp/EMS-ESP32/issues/3360)
- security: every `/api` call needs a sign-in token or an API key, also reads of values, `system/info` and metrics. Calls without one get HTTP 401 [#3360](https://github.com/emsesp/EMS-ESP32/issues/3360)
- security: opening an `/api` address in a browser asks for a sign-in (HTTP Basic). It only reads values, also for admins: changing values and running Commands need an API key. An API key also works as the password, with any username, for tools that only support Basic, for example `http://user:emsesp_...@ems-esp.local/api/boiler`. The key keeps its rights there, except in a browser, where it only reads. Failed sign-ins count towards the sign-in lockout, and a correct one is remembered for 5 minutes, in memory only
- security: reading the definitions of named Commands through `/api` (`/api/commands/values`, `/info`, `/entities` or `/api/commands/<name>/value`) needs a "Read and Write" API key. Integrations that read these without one get "authentication failed". Calling a command by name still runs it
- security: only admins can open or change the Scheduler, Commands, Custom Entities and Modules, rename devices or change entity customizations and log settings, or use admin actions such as exports and partition switching. Guests can still view the log
- security: each Command has a "Guests may run this command" option. Commands created before 3.10.0 keep guest access, new ones start without it. It applies to the WebUI and `/api`
- security: the live System Log needs a login
- security: the Super User password is removed. On the serial console `su` asks for a Web UI admin user's username and password, `passwd` is removed. The console `read` command needs admin
- security: telnet asks for a Web UI user's login, admin users get admin rights and `su` is only on the serial console. At most 2 telnet sessions, closed after 10 minutes idle. Telnet is off on new installs (upgrades keep their setting) and the Web UI shows a notice while it's on. Telnet is not encrypted, so use the Web UI or serial for admin work, or a VPN [#3358](https://github.com/emsesp/EMS-ESP32/issues/3358)
- security: repeated failed logins to the Web UI, telnet, serial `su` and the recovery firmware are slowed down, per source address and for all sources together. The Web UI sign-in answers HTTP 429 while locked out [#3362](https://github.com/emsesp/EMS-ESP32/issues/3362)
- security: to go back to 3.8.x or 3.9.x after upgrading, restore a System Backup made before the upgrade, as older versions can't read the hashed passwords. Without that backup, the [FAQ](https://docs.emsesp.org/FAQ#going-back-to-an-older-version) explains how to sign in with the serial console
- security: user passwords are stored hashed (PBKDF2-SHA256), existing passwords are converted on the first boot. The Web UI and `show users` no longer show stored passwords; leave a password field empty to keep the current one [#3355](https://github.com/emsesp/EMS-ESP32/issues/3355)
- security: settings exports and System Backups leave out passwords and keys, unless an admin ticks "Include passwords and keys". Restoring keeps the passwords already on the device; a restored user with no password can't log in until an admin sets one [#3356](https://github.com/emsesp/EMS-ESP32/issues/3356)
- the entity language list in Application Settings only shows the languages included in the firmware, for example only English and German on 4MB boards. `/rest/systemStatus` returns them as `languages`
- the security changes use less internal memory: their caches and limits are smaller and need no heap for locking, password and API key hashes are kept in PSRAM on boards that have it, `X-Content-Type-Options` and `Referrer-Policy` are only sent with the Web UI files, the unused space in the Web API route list is freed after startup, and the official build check runs once at boot
- CI release workflows sign the firmware in a separate job after the builds, so build tools and libraries never have the signing key
